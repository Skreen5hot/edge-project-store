# edge-project-store

A shared project folder for offline, edge-canonical data pipelines, and one small module that every tool in the
pipeline reuses to read and write it.

**Status:** contract **v0.2** (2026-11-04): the contract, its JSON-LD context and JSON Schemas, and 25 synthetic
example projects with their expected evaluation reports; v0.1 is kept at the tag `eps-v0.1`. Module (slice 2),
M1 (project folders on disk) and M2 (project folders in the browser) are built and validated; M3 (SDD project mode)
is SDD's. See [`PROPOSAL.md`](PROPOSAL.md) for the decisions and
[`MILESTONES.md`](MILESTONES.md) for the plan.

## The idea

A pipeline such as *source schema or sample data → normalized schema → Semantic Data Dictionary → RML → RDF →
graph* is run by several separate tools. Instead of each tool inventing its own way to save and reopen work, they all
use one **project folder** with a fixed layout:

- the user picks the folder (it can live in OneDrive, a network share or a git repository);
- each stage has its own subfolder with one responsible writer; `source/` is a shared intake area;
- committed state is never overwritten: artifacts, their records and the stage's revisions are only ever added
  (work in progress is the one mutable exception);
- every artifact has a record of the exact inputs it was built from, so any tool can tell, recursively, what is
  out of date and why;
- the contract governs how a project is kept, not how the pipeline is run: a tool may take any registered artifact
  as its input, whatever stage it is in;
- a file that cannot be read (for example an OneDrive file not downloaded while offline) is reported, and what
  depends on it is marked as not evaluated, rather than the whole project failing to open.

The tools share a **contract**, not a server, a database or a lock service. One pure evaluation turns a folder into a
report of what is current, out of date, in conflict, damaged, or not evaluable because a file could not be read.

## Using the module in a browser tool

A browser tool vendors these files, copied from one tagged commit and pinned by SHA-256. They are plain ES modules
with no dependencies and no imports outside this list, so they can be inlined into a single page:

| File | Needed for |
|---|---|
| `src/index.mjs` | the entry point |
| `src/contract.mjs`, `src/sha256.mjs`, `src/jsonschema.mjs`, `src/schemas.mjs` | the evaluation, names, canonical bytes and schemas |
| `src/project.mjs` | the writer rules: `loadTree`, `createProject`, `openProject` |
| `src/memory-backend.mjs` | a project in memory (tests, previews) |
| `src/browser-backend.mjs` | a project folder through the File System Access API |
| `browser/access.mjs` | optional: opening a folder, and the plain words when it cannot be opened (M2-c) |
| `browser/handle-store.mjs` | optional: remembering the folder across restarts (IndexedDB) |

`src/node-backend.mjs` and `src/summary.mjs` are for Node and the `eps` tool only. This list changes only with a new
module version.

**Module versions** are tags `eps-module-v<version>`; `eps-module-v0.2.0` implements contract v0.2. How the module is
packaged beyond that is the registrar's decision (M4).

**Committing only on what the person saw.** `commit()` and `merge()` take an optional `expectedHeads`: the stage's
heads (revision paths, as the report lists them) that the tool showed the person. If the heads differ when the write
starts, nothing is written and the call fails with `HEADS-CHANGED`; R-W5 (`STAGE-CHANGED`) covers the rest of the
write. Across origins and machines this narrows the window, as R-W5 does; it does not close it (§9).

## Principles

- **Offline and local.** No network requests, no accounts, no server. The files belong to the user.
- **Edge JSON-LD.** Metadata is JSON-LD with one fixed, versioned, local context.
- **Deterministic.** The same folder always evaluates to the same report; hashes identify content.
- **Honest guarantees.** The contract detects conflicts and damage across synchronized machines; it does not claim
  to prevent them.
- **Manual fallback.** Every tool keeps a plain open-file / save-file path where folder access is unavailable.

## Origin

The browser backend (`src/browser-backend.mjs`, with `browser/handle-store.mjs`) is adapted from the File System Access implementation in
[Skreen5hot/mermaid](https://github.com/Skreen5hot/mermaid) (CC0): atomic writes, Web Locks, path sanitization and
the permission lifecycle.
